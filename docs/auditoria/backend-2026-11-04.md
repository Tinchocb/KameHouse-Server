## Compatibilidad y operación

- Un TV/WebView que envíe `Origin: null` o `file:` necesitará contraseña en el
  servidor y las credenciales en el cliente. No hay manera de distinguir un
  webview legítimo de un iframe sandbox usando únicamente el valor `null`.
  Se inspeccionó el cliente local KameHouseTV: ya dispone de configuración de
  contraseña, cabeceras de token y autenticación WS. No se probó un TV físico.
- Tauri conserva `http://tauri.localhost`, `https://tauri.localhost` y
  `tauri://localhost`; el desarrollo conserva sus orígenes HTTP. No se obliga a
  configurar contraseña para esos orígenes por este cambio.
- Cambiar `corsOrigins` requiere reiniciar el servidor. Se evita presentar como
  hot-reload una actualización que dejaba políticas HTTP/WS distintas.
- No se cambiaron DTOs ni se regeneró el contrato TS.

## Cierre adicional solicitado

El plan y su ejecución están en `backend-2026-11-04-plan-cierre.md`.
Se agregaron pruebas con configuración de producción, HTTP y WebSocket reales
contra servidores efímeros, sin tocar la instancia ni los datos del usuario.

Esas pruebas reprodujeron un problema adicional: WebSocket consumía intentos de
autenticación antes de rechazar un origen externo. Ahora se valida el origen
primero, y el fallback de mismo Host reutiliza las reglas locales de la guarda
HTTP para rechazar DNS rebinding. Un hostname público legítimo debe figurar
explícitamente entre los orígenes permitidos.

También se comprobó que los probes compartidos sobreviven a la cancelación de
un cliente individual, entregan el resultado al cliente restante y se cancelan
y esperan al cerrar el extractor. Las reservas de pretranscode en espera de
cupo se cancelan durante shutdown sin fugas de cupos. Las pruebas de límites de
autenticación ahora aíslan su estado entre corridas repetidas.
