# O-03: aplanado de eras de AlternatingTimeline

Fecha: 25/10/2026. Estado: **medido; memoización aplicada por solicitud del usuario después de revisar los resultados**.

El aplanado no queda cacheado de forma independiente por React Compiler al cambiar el estado de detalles. Su coste mediano medido fue **0.02125 ms por interacción** con los 70 lapsos actuales. Se aplicó la variante B mediante `useMemo`, por solicitud del usuario. Las mediciones no demuestran una mejora global consistente.

- Chrome 155.0.8059.86, headless, 1440 × 900, DPR 1; sin throttling, movimiento normal y service workers bloqueados.
- React 19.2.7, React Compiler 1.0.0, Rsbuild 1.7.5.
- Dos builds de producción con el plugin React/Babel y configuración de división de chunks del proyecto. Se usó react-dom/profiling para obtener duraciones de commits. No es el bundle ordinario de distribución.
- Fixture aislada: AlternatingTimeline y sus descendientes reales, datos VOLUMES_DATA completos (70 lapsos, 5 eras) y CSS del proyecto. No incluye el shell de la aplicación.
- No había instancias escuchando en los puertos de aplicación consultados. No se arrancó ni consultó la biblioteca real. La API se respondió con fixtures de lectura y las imágenes externas con un pixel local.
- Mismo número de nodos al finalizar cada ventana: 1490. Sin errores de página ni intentos de escritura.

## Comparación

A = código actual. B = useMemo de volumesByEra dependiente solo de eraGroups, con lectura por índice dentro del map de render. B se aplicó en memoria mediante un loader, sin editar el archivo del repositorio.

Se hicieron ocho corridas en navegadores nuevos, orden A/B/B/A/A/B/B/A. Cada una incluyó cuatro interacciones de calentamiento y veinte cambios medidos de apertura/cierre de detalles del primer lapso, separados por al menos 250 ms.

El contador y el cronómetro del flatMap se insertaron **después** de React Compiler, sobre el JavaScript generado. De esta manera el contador no cambia las decisiones de memoización del compilador. La instrumentación añade coste y está sujeta a la resolución de performance.now; las cifras no son precisión de laboratorio.

## Evidencia del compilador

En A, el flatMap está dentro del bloque de JSX cacheado que depende, entre otros valores, de openDetailsId y volumeDetailTabs. Por eso se vuelve a ejecutar cinco veces por cambio de detalles. En B, el cálculo queda en un bloque separado dependiente de eraGroups y no se repite durante la ventana. Ambas variantes contienen react/compiler-runtime.

## Decisión y límites

- O-03 aplicada por solicitud del usuario: el aplanado se conserva mientras `eraGroups` no cambie. El ahorro medido sigue siendo pequeño y no demuestra una mejora global consistente.
- Reabrir si aumenta considerablemente el número de lapsos/eras o si un perfil de la aplicación completa identifica este cálculo como relevante.
- No se midieron INP ni LCP de la aplicación completa, scroll sostenido, reproducción, Tauri/WebView2 ni otros dispositivos. El conteo de commits incluye actualizaciones de descendientes y no equivale al número de renders de cada fila.
- Los tiempos incluyen la sobrecarga de React profiling, la instrumentación y la traza, iguales entre variantes. No constituyen tiempos del bundle ordinario.
